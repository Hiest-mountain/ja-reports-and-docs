# 作業の過程を見ていない人が読む日本語を書く

読み手は判断か行動のために読む。必要な情報を選別して、優先順位の高い順に書く。残した情報の数値や名前はぼかさない。セッション内の報告も作業の過程を見ていない人に向けて書く。

| 段階 | 行うこと | 読むもの |
|---|---|---|
| 書く前 | 情報を選別して優先順位を付ける | 1 節、`doc-types.md` |
| 書く前 | 構成を決める | 2 節、`tables.md` |
| 書くとき | 語、主語、語順、読点を読み手に合わせる | 3 節 |
| 書いた後 | 削る役のサブエージェントに削らせて、読み手役のサブエージェントに読ませて、最後に文を 1 文ずつ点検する | `check.md` |

書いた後の点検は省かない。書きながら 3 節を守ったつもりでも、経緯の文や重複や言いさしの読点は残る。サブエージェントを起動できないときは、書き手が `check.md` の冒頭にある 4 つの操作を自分で行う。完成を報告するときは、削った文の数と検索で直した箇所の数を添える。数を書けないなら、その点検はまだ終わっていない。

文書の種類ごとに行う段階は、`doc-types.md` の「適用する範囲」の表にある。既存の文書を書き直すときは、先に `rewrite.md` を読む。項を変えるか消すかで迷ったら、`evidence.md` で各項の根拠を読む。

## 1. 伝える情報を選別する

同じ分野の知識があって説明する対象の詳細は知らない人を、既定の読み手とする。関心のある情報は、その人が読んだ後に何をするかで決まる。

| 読み手が読んだ後にすること | 関心のある情報 |
|---|---|
| 自分で作業を進める | 手順と詳細 |
| 可否や方針を判断する | 結果、目標、リスク |
| 使うかを決める | どの範囲にどんな影響があるか |

1. 読み手と読む目的を決める。多くはセッションの流れから分かる。分からなければ依頼者に聞く。読み手の用事は文書の種類ごとに `doc-types.md` に載っている。
2. 読み手が読みながら順に持つ問いを 3 つか 4 つ書き出す。問いは、材料を読む前に文書の種類と 1 行の説明だけから書き出す。材料を読んでから問いを書き出すと、材料の項目ごとに問いができて全部の事実が載ってしまう。この skill の README なら「日本語を直す skill だと分かった。具体的にどう修正するのか。どの範囲で動作するのか。どういう動作をするのか」になる。
3. 文書には問いの答えを問いの順に書く。どの問いの答えにもならない事実は載せない。
4. 答えに要る情報を挙げて、優先順位を付けて高い順に書く。優先順位は同じ種類の情報の束に付ける。読み手に求める操作が 2 つあれば、2 つを隣に並べるか 1 つの行動にまとめる。間に所要時間のような別の種類の情報を挟むと、2 つが同じ注意だと読み手に伝わらない。
5. その文書や段落に収まらない優先順位の低い情報は載せない。後で要る情報は別の文書へ移して、元の文書から 1 行で案内する。案内先は実在する文書に限る。
6. 文を書く前に、材料にあって今回の文書には載せない事実を 3 つ以上書き出す。経緯、作者が一度測った数値、作者に固有の用途、内部の分岐の細部が候補になる。完成を報告するときは、書き出した数も添える。

段落の中でも、1 文ごとに残す必要があるかを判断する。「この文が無いと読み手は何に困るか」に答えられない文は削る。

選別は 3 節の書き方より先に行う。数値が具体的なことや理由が付いていることは、その情報を載せる理由にならない。作者が一度測った量、過去の不具合とその対処、設計の意図は、読み手の操作か判断を変えるときだけ残す。

| 残す情報 | 載せない情報 |
|---|---|
| 知らないと操作に失敗する条件 | 画面を見れば分かること |
| 待つ時間や量の見当 | 問題が起きたときに画面が表示すること |
| 読み手の判断を変える制約 | 書かなくても予想できる結果 |
| 途中でやめる方法、元に戻す方法 | 設計の理由、内部の仕組み |
| このツールに固有の、事故を防ぐ注意 | 一般論の注意と定型の免責（規約に照らして判断する、購入前に確認する） |
| 推奨する設定と、その設定にする操作 | 推奨しない設定にした場合の失敗の説明 |
| 読み手が変更する設定項目と既定値 | 読み手の操作を変えない内部の数値と分岐（再試行の回数、待ち時間の倍率、解析の規則） |

手順には、操作した後に成功と判断できる表示を書く。「しばらくするとブラウザが開いて地図が表示されます」は画面を見れば分かるが、削ると読み手は成功したかを判断できない。

残した事実が同じ行動を求めるなら、読み手の行動 1 つにまとめる。

数値と名前はぼかさない。「数分かかる」を「時間がかかる場合がある」に変えない。

ブラウザ拡張の README から、実行ボタンを押した後の説明を例に取る。元の資料には事実が 8 つあった。

| 版 | 文 |
|---|---|
| 事実を 4 つに選別した版 | 件数が多いと、収集に数分かかります。収集中はスクロール操作をせず、タブを表示したままにしてください。X は表示されていないタブでは次のページを読み込まないので、別のタブに切り替えると収集が進みません。 |
| 作者が書いた版 | 件数が多い場合は数分かかりますが、収集中はブラウザの操作をしないでください。 |

作者の版は「スクロールしない」と「タブを切り替えない」を「ブラウザの操作をしない」という 1 つの行動にまとめて、仕組みは載せていない。

言い切りの文が 3 つ以上並ぶ段落では、載せない情報が残っていないかを先に確かめて、その後で文の形を直す。

## 2. 構成を決める

- 冒頭の 1〜3 文で、`doc-types.md` の「冒頭で答える問い」に答える。README に起動方法の 1 行が無ければ、ほかの修正より先にその 1 行を足す。
- 節は読み手が使う順に並べる。作業の順番と失敗の経緯と設計の考え方は、使い方の後ろか別の文書に置く。
- 見出しにはその種類の文書で慣習になっている節の名前を使う。README なら「動作環境」「必要なソフトウェア」「インストール」「使い方」「設定」「ライセンス」である。「Python と現像ソフトが要る」のような文の形の見出しは使わない。記事と調査報告では、出来事や判断を述べる文の形の見出しを使う。
- 読み手が途中で替わる文書は節を分ける。使う人向けの節を先に置いて、改造する人向けの節は後ろにまとめる。見出しには対象の読み手を書く。
- 読み手が操作する前に知る必要のある禁止は、その操作を説明する節の冒頭か、文書の冒頭に置く。文書の末尾の注意にまとめると、読み手は読む前に操作してしまう。
- 用語の定義はその用語を使う表や手順の直前にまとめる。
- 段落を書く前に、その段落で伝える要点を 1 つ決める。要点が 2 つあれば段落を分ける。
- 同じ種類の情報が項目ごとに繰り返されるなら表にする。表の作り方は `tables.md` にある。

## 3. 文を書く

### 3.1 語を一つの意味に固定する

| 対象 | 確かめること | 直し方 |
|---|---|---|
| 会話の中で決めた呼び名（処方、台帳、外出、担当、案） | その分野で定着した呼び名があるか | あれば置き換える。無ければ初出で実体を先に説明してから名前を付ける。新しい名前は 1 段落に 1 つまで |
| 意味が複数ある動詞（動かす、立てる、起こす、当てる、詰める、写す、回す、落とす） | 文書の中で 2 つ以上の意味に使っていないか | 意味ごとに一つに決まる語へ置き換える |
| 意味の広い名詞（物、所、形、手、感じ、辺り） | 見出しや主語に使っていないか | 指している対象の名前に置き換える |
| 同じ対象の別名（担当、サブエージェント、あなた） | 一つの対象を複数の名前で呼んでいないか | 一つの名前にそろえる |

定義の書き方の例: 「写真 1 枚の補正値を JSON ファイルに記述する。このファイルを処方と呼ぶ。」

### 3.2 ソフトウェアの動作と操作は意味の狭い語で書く

ソフトウェアの動作と利用者の操作には、技術文書で定着した意味の狭い述語を使う。和語の動詞は意味が広いので、読み手ごとに解釈が分かれる。下の表は例なので、表に無い動詞も同じ基準で判断する。動作か操作を和語の動詞で書いていたら、意味が一つに決まる語があるかを確かめて置き換える。

| 会話の語 | 文書で使う語 |
|---|---|
| 始まる、動く、動かす | 起動する、実行する、処理を開始する、動作する |
| 終わる | 完了する、終了する |
| 並ぶ、できる、出てくる | 出力される、保存される、生成される |
| 選ぶ | 選別する、選択する |
| 試す、確かめる | 検証する、動作を確認する |
| 見比べる | 比較する |
| 入れる、置く | インストールする、配置する |
| 直す、変える | 修正する、変更する |
| 書く（設定を） | 指定する、設定する、記述する |

右の列に語が複数ある行では、文の中で意味が一つに決まる語を選ぶ。

次の 2 つは和語のまま書く。

- 対象の分野で定着した和語。写真なら「書き出す」「仕上げる」「切り抜く」。
- 作者の判断や状況を述べる文。「作者の環境で使い始めたところです」を「使用を開始した段階です」にすると、規程の文書のように読める。

### 3.3 主語と目的語を書く場面

主語は次の場面で書いて、ほかでは省く。

- 文や手順の途中で動作の主体が替わる
- 主体が人かプログラムかを読み手が見分けられない
- その主体が文書に初めて出てくる

作者の判断は理由と一緒に 1 文で書く。「商用利用が出来ないライセンスなのでジェネレータからは除外しています」のように書けば、主語の「作者」は書かなくても伝わる。

手順書では、各段階の主体を「利用者」「Claude」「サブエージェント」「スクリプト」のどれかに決めて、主体が替わる段階でその主体を書く。

他動詞には目的語を書く。「写真が無いうちは飛ばしてよい」は、省く対象を補って「評価用の写真が無い場合、この比較は省略できる」と書く。

### 3.4 語順と文のつなぎ方

- 主題を文の先頭に置く。長い修飾を主題の前に重ねると、何の文かが文末まで分からない。
- 係る語と受ける語を近くに置く。修飾が複数あれば長いほうを先に置く。それでも長ければ文を分ける。
- 判断の根拠、条件、例外は主文に書く。括弧の中や文末に置くと読み落とされる。型番やファイル名は括弧に入れてよい。
- 因果、順序、対応、並列の関係は、`→` `=` `/` `—` で代用せずに語で書く。
- 太字は 1 段落に 1 箇所までにする。
- 言い換えても条件、限定、確度は変えない。「だけ」「未確認」「推定」を落とさずに、根拠より強く言い切らない。

括弧と記号と太字の 3 つの項は地の文だけに適用する。

文は段落の中でつないで書く。

- 理由と結果は「ので」「ため」でつないで 1 文にする。例は前の文につなぐ。事実を 1 つ書くたびに文を切ると、短い言い切りの文が並んで箇条書きを文にしただけになる。
- 文書が自分の中身を予告する文は書かずに、中身を書く。「載せる情報、構成、語を定めています」「次の 2 つを実行します」は中身が無い。
- 文末の表現は内容に応じて使い分ける。「です」「しました」「あります」「してください」「しています」を使い分ける。「〜します」だけが続く場合は、主語が全部 Claude かソフトウェアになっている。

次の型は読み手が不自然に感じるので、右の列の文のように書き直す。表は型の例なので、語が違っても同じ構造の文は書き直す。

| 型 | 例 | 書き直した文 |
|---|---|---|
| 要点を文末に置く「〜のは…である」 | 動作を確認できているのは、次の組み合わせだけである。 | 次の組み合わせでのみ動作を確認している。 |
| 長い修飾を名詞にかけて「〜の、A です」「〜する A です」で終える | 写真を自動で補正するツールの README にこの skill を適用したときの、修正前と修正後の文です。 | 写真を自動で補正するツールの README をこの skill で修正したところ、文は次のように変わりました。 |
| 動作を名詞に包む「〜することを目的として」 | 読んで理解できる文章にすることを目的として、書き方を定めています。 | 読んでも理解できるように、書く前に載せる情報を選別します。 |
| 物を主語にした他動詞の文 | 何がそれを邪魔しているのかを読む。 | その理由が伝わりにくくなっている原因を特定する。 |
| 文の途中で主語が替わる | 写真を一覧画像に並べ、サブエージェントが点数を付けて選ぶ。 | スクリプトが写真を一覧画像に配置する。その一覧をサブエージェントが評価して写真を選別する。 |
| 主語の係り先が 2 通りに読める | 別のサブエージェントが補正値を書いた JSON ファイルを作る。 | 別のサブエージェントが補正値を JSON ファイルに記述する。 |
| 「A と B を〜する」の述語が片方にしか係らない | 配布用の版と、範囲の指定を円に置き換える。 | 2 つの commit に分けるか、A と B のそれぞれに動詞を付ける。 |

### 3.5 読点を打つ位置

- 短い文では主題の直後に読点を打たない。「この skill は現像ソフトの CLI を起動して現像の命令を送信する。」
- 主題が長いときと、読点が無いと係り先を読み違えるときは、主題の直後に読点を打つ。
- 読点が無いと読みにくい語順になったら、読点を足す前に語順を見直す。「README に、内部で使用するフォントの名前を記載する」は「内部で使用するフォントの名前を README に記載する」と書けば読点が要らない。
- 動作を順に続けるときは「〜して」でつないで、前後が短ければ読点を打たない。「書く前に載せる情報を選別し、書いた後に語と読点を点検する」は「書く前に載せる情報を選別して書いた後に語と読点を点検する」と書く。「〜し、」と言いさして読点で続けると、文が 2 つに割れて見える。1 文に動作を詰め込んで前後の関係が曖昧になるのを防ぐための項で、連用中止が文法的に誤りだという意味ではない。前半が「〜して」の直後の語に係って読める場合は読点を残す。
- 読点が 3 つ以上ある文は、用件が 2 つ入っているか、列挙を文の途中に埋めている。文を分けるか、列挙を箇条書きに移す。

### 3.6 読み手が最初に必要とすることから書く

段落と文は、読み手がその時点で最初に知る必要のあることから書く。多くの場合、それは読み手が行うことか、対象が今どう動作するかである。書き手の頭の中にある順番、つまり既定と例外、前の版と変更、禁止と代わりの順で書くと、経緯を知らない読み手は結論を後から組み立てることになる。

否定、例外、以前の姿との比較を含む文には、表現の形にかかわらず次の 2 つを順に当てる。

1. 否定や例外の側を消して肯定の文だけを読んだとき、読み手は誤った行動や判断をするか。しないなら、並べ替えずに否定や例外の側を削る。
2. 残すなら、先に読まないと読み手が事故を起こすか後ろの文を誤解するかを確かめる。次の場面では否定や制約を先に置く。それ以外は、行うことか現在の姿を先に書いて、制約を後ろに置く。
   - 実行する前に止める必要がある禁止。本番環境での操作、データの消去、元に戻せない操作が当たる
   - 読み手が誤解していると分かっている前提の訂正
   - 対応していない環境など、対象外の読み手の振り分け

並べ替えても条件、限定、確度は保つ。元の材料に無い理由は足さない。経緯は後ろに回して残すのではなく、1 節に従って削る。

「A は B である。C ではない。」と肯定と否定を並べて範囲を示す文も、1 の判定で否定の文を削れることが多い。読み手が知るべき制約（上書きされない、未確認の環境がある）は、独立した事実として書く。

### 3.7 書き手の環境と経緯は、読み手にとっての意味に書き換える

書き手の環境や経緯を書きたくなったら、その事情が読み手の作業や判断にどう影響するかを書く。

| 書き手の事情を書いた文 | 読み手にとっての意味を書いた文 |
|---|---|
| 作者の環境は Windows 11 と Python 3.12。 | Windows 11 と Python 3.12 の組み合わせで動作を確認している。これ以外の環境での動作は未確認である。 |
| 作者は開発版の現像ソフトを使っている。 | 被写体のマスクとノイズ除去は、リリース版の現像ソフトでの動作が未確認である。 |
| このスクリプトは作者の確認用。 | このスクリプトは現像ソフトを差し替えた場合に使用する。 |

書き換えても読み手に伝える意味が残らない文は削る。作者の判断を理由と一緒に述べる文は 3.3 に従って書くので、この項の対象外である。

### 3.8 作業の中でしか通じない情報を外す

次の情報には説明かリンクを付ける。付けられなければ消す。

- 作業中に Claude が付けた呼び名（スクリプトの名前、版の名前、分類の名前）。依頼者もこの呼び名を見ていないので、セッション内の報告でも説明を付ける
- 決定番号と内部の節名（「D-012」「手順書の『2 回目の設定』」）
- 作業中に数えた数（「267 枚のほぼ全部で」）
- 時間の相対表現（「前回」「今回」「さっきの」）
- 失敗の経緯。要るなら文書の末尾か別の文書に置く

セッション内の報告では、依頼者との会話に出た語と「前回」「今回」はそのまま使ってよい。

### 3.9 文体をそろえる

- 新しく作る文書は敬体で書く。既存の文書を直すときは元の文体に合わせる。
- 常体と敬体は一つの文書の中でそろえる。
- commit の件名には敬体を使わずに、動詞の終止形で終える。
- 公開する文書では一人称「僕」を使わない。
- commit の言語はそのリポジトリの直近の commit の多数派に合わせる。

## 4〜6. 書いた後に点検する

`check.md` に従って 3 つの点検を順に行う。4 節で要らない文を削って、5 節で読み手に伝わるかを確かめる。最後に 6 節で文を点検する。書きながら 3 節を守ったつもりでも崩れは残るので、6 節は省かない。
